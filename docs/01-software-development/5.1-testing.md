# Testing

!!! info "What You Need to Know"

    For Higher Software Design and Development, you must be able to:

    - create and use a **comprehensive final test plan** to check the **functional requirements**
    - identify **syntax**, **execution**, and **logic** errors
    - explain and give examples of **dry runs**, **trace tables/tools**, **breakpoints**, and **watchpoints**

Testing means checking that a program does what it is supposed to do.

For example, a program might run without crashing but still give the wrong answer. Testing helps you spot this before someone relies on the result.

The key question is: **“Does the program do everything it is supposed to do?”**

## Testing and Debugging

**Testing** means checking for mistakes. **Debugging** means finding out what caused a mistake and fixing it.

| Activity | Example |
|---|---|
| **Testing** | Enter a mark of `50` and check that the program displays `Pass`. |
| **Debugging** | Find that the program uses `mark > 50` when it should use `mark >= 50`. |

Once you fix a mistake, repeat the test. Check some other values too, in case your change has caused a different problem.

## What Is a Test Plan?

A __test plan__ is a table showing what you will enter into a program and what you expect it to do.

After running each test, you add what actually happened.

Plan your tests **before writing the code**, once you know what the program must do. This helps you think about the right answers before you start programming. Add or adjust tests if the requirements change.

| Term | What it means |
|---|---|
| **Test data** | The values you use to check the program. |
| **Expected result** | What the program should do. Work this out before running the test. |
| **Actual result** | What the program really does when you run the test. |
| **Pass or fail** | Whether the actual result matches the expected result. |

A **final** test plan checks the finished program. **Comprehensive** means that it checks everything the program is required to do, using enough different tests to find likely mistakes.

## What Should You Test?

Start with the **functional requirements** from [analysis](2.1-analysis.md). These describe what the program must do.

Suppose a program must:

1. Accept a whole-number mark from `0` to `100`. If the entry is not allowed, show an error message and ask again.
2. Decide whether the mark is a pass. A mark of `50` or above is a pass.
3. Display the mark and either `Pass` or `Not yet passed`.

Your tests need to check **all three requirements**. Checking only that the program accepts a mark would miss mistakes in the pass decision or the displayed result.

!!! note "Worked Example"

    This mark-checking program is a teaching example. Its pass mark of `50` is a rule chosen for the example, not a statement about SQA grade boundaries.

## Testing the Parts and the Whole Program

When a program uses functions or procedures, check each one on its own first. This makes it easier to find which part contains a mistake.

For the mark-checking program, suppose a function called `get_result(mark)` returns either `Pass` or `Not yet passed`.

| What are you testing? | What would you check? |
|---|---|
| **The function on its own** | Give `get_result` a mark of `49`, `50`, and `51`. Check that it returns the correct message for each one. |
| **The parts working together** | Enter `50` through the main program. Check that this mark is passed to the function and that the returned message is used in the displayed result. |
| **The whole program** | Enter an incorrect value, then a correct mark. Check that the program asks again, makes the right pass decision, and displays the correct mark and message. |

A function could return the right answer while the main program displays an old value or the wrong message. That is why you need to check the parts **working together**, as well as separately.

## Choosing Test Data

You will already have met **normal**, **extreme**, and **exceptional** test data. They are useful when building your Higher test plan.

| Type | What it means | Example for a mark from 0 to 100 |
|---|---|---|
| **Normal** | A typical value that is allowed. | `65` |
| **Extreme** | The lowest or highest value that is allowed. | `0` and `100` |
| **Exceptional** | A value or entry that is not allowed. | `-1`, `101`, `hello`, or an empty entry |

For this program, `0` and `100` must be **accepted**. Values such as `-1` and `101` must be **rejected**.

!!! note "Remember"

    Extreme values are still valid. They sit at the limits of the allowed range.

    Exceptional values break an input rule.

### Check Where a Decision Changes

The program makes a different decision when the mark reaches `50`. Check values just below, exactly at, and just above that point.

| Mark | Expected result | Why use it? |
|---|---|---|
| `49` | `Not yet passed` | Just below the pass mark. |
| `50` | `Pass` | Exactly at the pass mark. |
| `51` | `Pass` | Just above the pass mark. |

This is useful for spotting a mistake such as using `> 50` instead of `>= 50`.

These are valid marks, but they are not the lowest and highest allowed inputs. They test the **pass decision** rather than the ends of the input range.

| T3 | The lowest allowed mark. | `0` | Accept the mark; display `0` and `Not yet passed`. |  |  |

!!! note "Exam Tip"

    Give a clear expected result. **“Displays 50 and Pass”** is more useful than **“Works correctly.”**

    Choose tests that match the question. If the question says the input is already valid, do not assume the program must check every possible incorrect entry.

### Recording a Failed Test

Suppose you enter `50` but the program displays `Not yet passed`.

| Test | Expected result | Actual result | Pass or fail? |
|---|---|---|---|
| T6 | `50` and `Pass` | `50` and `Not yet passed` | Fail |

You now know which case is wrong. Look at the code that decides whether a mark is a pass.

After fixing it, repeat T6. Also check `49` and `51` to make sure the nearby values still give the right results.

Keep a record of the first result and the result after the fix. Do not change a failed result to a pass without running the test again.

## Types of Error

### Syntax Errors

A __syntax error__ means the code breaks a rule of the programming language.

For example, Python needs a colon at the end of an `if` statement:

```python
if mark >= 50
    print("Pass")
```

The colon is missing, so Python cannot run this script. The corrected code is:

```python
if mark >= 50:
    print("Pass")
```

### Execution Errors

An __execution error__ happens while the program is running. The code follows the language's rules, but it tries to do something that cannot be carried out.

```python
scores = [12, 18, 15]
print(scores[3])
```

This list has three items, at positions `0`, `1`, and `2`. Position `3` does not exist, so Python reports an `IndexError` when it reaches that line.

Dividing a number by zero is another example of an execution error.

### Logic Errors

A __logic error__ means the program runs but does the wrong thing.

```python
if mark > 50:
    print("Pass")
else:
    print("Not yet passed")
```

The rule says that **50 or above** is a pass. This code displays `Not yet passed` for `50`, because `50 > 50` is false.

Change the condition to `mark >= 50` to include a mark of exactly `50`.

### Comparing the Three Types

| Error | Simple explanation | Example |
|---|---|---|
| **Syntax** | The code is written incorrectly. | A missing colon after `if`. |
| **Execution** | Something goes wrong when a line runs. | Trying to use a list position that does not exist. |
| **Logic** | The program runs but gives the wrong result. | Rejecting `50` as a passing mark. |

!!! note "Exam Tip"

    Explain the mistake in the question, not just the name of the error.

    For example: **“This is a logic error because a mark of 50 should pass, but the condition only accepts marks greater than 50.”**

## Finding and Fixing Errors

The four techniques below help you find where a program goes wrong.

### Dry Runs

A __dry run__ means working through the code by hand, without running it on a computer.

Choose some test data and follow the instructions in order. Work out each decision and calculation as you go.

For the faulty pass condition:

1. Use a mark of `50`.
2. Check the condition `mark > 50`.
3. `50 > 50` is false, so follow the `else` branch.
4. The output is `Not yet passed`, which is wrong for this mark.

### Trace Tables and Tools

A __trace table__ records variable values as you work through the code. It helps you see exactly when a value becomes wrong.

Consider this program, which is meant to add three scores:

```python
scores = [10, 15, 20]
total = 0

for score in scores:
    total = score

print(total)
```

The correct answer should be `45`. However, the program prints `20`.

| Point in the program | `score` | `total` in this program | What the running total should be |
|---|---|---|---|
| Before the loop | Not yet set | `0` | `0` |
| After the first repeat | `10` | `10` | `10` |
| After the second repeat | `15` | `15` | `25` |
| After the third repeat | `20` | `20` | `45` |

The problem is `total = score`. It replaces the total with the latest score each time.

To add each score to the total, use:

```python
total = total + score
```

The total will then change from `0` to `10`, then `25`, then `45`.

A dry run is the **working-through process**. A trace table is one way to **write down what happens**. Debugging tools can also show variable values while a program runs.

### Showing Decisions in a Trace Table

You can also include the **True** or **False** result of a condition. This helps you see which branch of an `if` statement will run.

For the correct condition `mark >= 50`:

| `mark` | Is `mark >= 50` True or False? | Message displayed |
|---|---|---|
| `49` | False | `Not yet passed` |
| `50` | True | `Pass` |
| `51` | True | `Pass` |

Each row is a **separate run** of the mark-checking program with a different input.

Compare this with the faulty condition `mark > 50`. For a mark of `50`, that condition is **False**. The table helps you explain why the wrong message would be displayed.

### Breakpoints

A __breakpoint__ tells the debugger to pause the program at a chosen line. A debugger is a tool in your programming editor that helps you inspect a running program.

While the program is paused, you can check variable values and run the next instruction one step at a time.

For the mark-checking program:

1. Put a breakpoint on the line containing `if mark > 50:`.
2. Run the program and enter `50`.
3. When it pauses, check the value of `mark`.
4. Step through the decision and see which message is displayed.

Many debuggers pause **before** the selected line runs. Check this when deciding what you expect the variables to contain.

### Watchpoints

A __watchpoint__ tells a debugger to pause when a watched value changes, or when a chosen condition involving that value is met.

For the total program, you could watch for changes to `total`. Each pause lets you check its new value. You would see `10`, then `15`, then `20`, which helps reveal that the scores are not being added together.

!!! note "Watching a Variable"

    A **watch window** shows variable values while you debug. A **watchpoint** tells the program when to pause.

    Adding a variable to a watch window does not always make the program pause when it changes. The tools available depend on your editor.

### Which Technique Would You Use?

| Technique | What you do |
|---|---|
| **Dry run** | Follow the instructions by hand. |
| **Trace table/tool** | Keep track of variable values as the instructions are followed. |
| **Breakpoint** | Pause at a chosen line and inspect what is happening. |
| **Watchpoint** | Pause when a watched value changes or a chosen condition is met. |

## Testing Programs That Use Arrays

Think about where a mistake might be hidden. For example, a loop might miss the last item in an array.

| Program task | Useful tests |
|---|---|
| Find a value using a **linear search**. | Put the value first, in the middle, and last. Also search for a value that is not there. |
| Find the **maximum or minimum**. | Put the answer at different positions. Also try an array where all values are equal. |
| **Count occurrences** of a value. | Try no matches, one match, several matches, and every item matching. |
| Display information from **records**. | Check that the displayed name and score belong to the same person. |

For example, the maximum in `[14, 9, 21]` is `21`. If a program reports `14`, check whether its loop reaches the last item.

Choose tests that fit the stated rules. Only test an empty array or negative numbers if the program is required to handle them.
